Inside the compilerFollow one PostgreSQL dependency through the planned layers.

  1. 01 / ADAPTER → CORE

    Evidence: what the app reveals

    The framework adapter hands off a versioned JSON document through a local process or file. It includes findings, their source, and anything the adapter could not determine. The core validates the contract before using it.

    Observed in the buildapi: PostgreSQL driver detectedStill unknown: who manages the database?

  2. 02 / RESOLVER & POLICY

    Application IR: what you intend

    The resolver combines evidence with infra.yaml, checks for conflicts, and builds a graph of services, resources, and bindings. Each decision points back to its source. IDs and ownership stay the same across targets.

    One binding in the IRapi → primary-dbPostgreSQL · managed · retain on removal

  3. 03 / CORE ↔ TARGET BACKEND

    Deployment Plan: what the target can do

    The selected backend receives the validated IR and target settings. Its capability checks inform a target-specific plan: expected resources, prerequisites, and planned files. An unsupported requirement blocks planning instead of being silently dropped.

    Kubernetes plan prerequisiteCloudNativePG operator requiredThe plan previews output; it is not a live state diff.

  4. 04 / RENDERER → YOUR WORKFLOW

    Artifacts: what you deploy

    The renderer uses the plan to write standard files. The same inputs produce the same output, with references to secrets instead of secret values. Building an image and applying changes are separate steps you control.

    Compose
    PostgreSQL service + named volume
    Kubernetes · planned
    CloudNativePG Cluster + operator-managed storage
    NixOS
    Importable app module with managed or external PostgreSQL.

05 / WHERE IT FITSTHE TOOLCHAIN

Keep your framework.

magic-infra aims to fill the gap between your existing application and your deployment workflow. It explains what the app needs, asks you who should manage it, and produces files you can take over.

01 / ALTERNATIVES

App SDKs & IaC

NitricInfrastructure via an app SDK

Good fit: You want to declare resources in application code and map them to deployment providers, including custom ones.

Difference: SDK calls express intent directly. magic-infra would read the conventions of frameworks you already use and ask about ambiguous signals, without requiring Nitric-style declarations in app code.

Nitric infrastructure docs ↗
EncoreIntegrated Go and TypeScript backend

Good fit: You want an integrated Go or TypeScript framework with local infrastructure. The managed platform is optional; Encore also documents Docker self-hosting.

Difference: Encore derives its model from its own primitives. magic-infra starts with the app framework you already use and plans the services and bindings for your Compose or Kubernetes target.

Encore platform and self-hosting docs ↗
SSTProgrammable infrastructure in TypeScript

Good fit: You want to model a custom topology in TypeScript using a broad provider ecosystem.

Difference: SST gives you control over the resources you define and tracks their state. magic-infra would suggest common resources from the app and generate deployment files, with a narrower supported catalog.

SST provider docs ↗

02 / WORKFLOW

Specs & dev loops

ScorePortable workload specification

Overlap: Score starts from a workload spec and can target Compose or Kubernetes. magic-infra starts from framework evidence and adds explicit ownership and a plan.

Possible fit: Export what maps to Score. Its implementations can provision resources during generation, so any reuse must preserve our separation between planning and applying.

Score implementation docs ↗
TiltFast local feedback for containers

Good fit: You already have Compose or Kubernetes files and want fast rebuilds, live updates and logs while developing.

Possible fit: Point a Tiltfile at the generated artifacts. magic-infra describes what the app needs; Tilt takes care of the local feedback loop.

Tilt and Docker Compose docs ↗

03 / OPERATIONS

Deploy & provision

CoolifySelf-hosted deployment dashboard

Good fit: You want a web UI to deploy and manage apps on your servers. Coolify can deploy Compose from Git.

Possible fit: Let magic-infra produce the files and Coolify deploy them. Verify proxy configuration, secrets and persistent volumes first.

Coolify Compose docs ↗
DokployDocker and Swarm deployment workflows

Good fit: You want to manage Docker deployments through a web UI. Dokploy has separate Compose and Swarm modes.

Possible fit: Test generated files in Compose mode. Swarm has different deployment semantics and would need separate support.

Dokploy Compose docs ↗
PulumiProvision and own external infrastructure

Good fit: You need programmable infrastructure for cloud networking, access policies or managed services.

Possible fit: Pulumi provisions and owns PostgreSQL. magic-infra would bind the app to that external database by endpoint and secret reference, without managing it.

Pulumi stacks and outputs docs ↗
